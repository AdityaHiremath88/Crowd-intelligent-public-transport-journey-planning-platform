## Research and technical references

- **Official GTFS Schedule specification:** [Reference](https://gtfs.org/documentation/schedule/reference/). Governs fields, required/conditional files, times, calendars, transfer and frequency semantics.
- **Official GTFS Realtime specification:** [Reference](https://gtfs.org/documentation/realtime/reference/). Vehicle positions/trip updates are not available in the project without authorized access and keys.
- **GTFS Realtime Python bindings:** MobilityData's [Python generated bindings](https://github.com/MobilityData/gtfs-realtime-bindings/blob/master/python/README.md), package `gtfs-realtime-bindings==3.0.0`, Apache-2.0. The binding parses protobuf bytes; it does not provide an authorized feed, validate Delhi identifiers, or estimate vehicle arrivals. `protobuf==7.36.2` is pinned as the compatible runtime declared by the binding version used here.
- **Delhi OTD timetable caveat:** [OTD documentation](https://otd.delhi.gov.in/documentation/) says static arrival/departure times are rough estimates under a constant-speed assumption.
- **MobilityData validator:** [open-source validator](https://github.com/MobilityData/gtfs-validator), Apache-2.0 software. It is a validator tool, not a feed licence; its output should supplement project-specific route/query invariants.
- **RAPTOR:** Delling, Pajor, Werneck (2015), [Round-Based Public Transit Routing](https://pubsonline.informs.org/doi/10.1287/trsc.2014.0534), DOI 10.1287/trsc.2014.0534. Round-based timetable routing enumerates Pareto-efficient arrival/transfer tradeoffs; it is relevant if and when a real feed and network-size benchmark justify replacing the current enumerator.
- **Delhi bus demand research:** [Public Transport Operations After Lockdown](https://pmc.ncbi.nlm.nih.gov/articles/PMC7290149/) reports a Delhi case study using one month of DIMTS ETM data for route-level demand analysis. It demonstrates potential for demand analysis, not validation of the current October file's field semantics or individual occupancy.
- **Indian ETM field heterogeneity:** Fedujwar et al., [From Variability to Uniformity: Standardization of Electronic Ticketing Machines Data for Urban Transit Systems in India](https://faculty.iitr.ac.in/~amitfce/pdfs/FedujwarEtc2025ETMStruCTRG.pdf). Discusses differences in ETM fields and inconsistent date/time, route/trip and stop references; motivates schema and semantic review before cross-operator generalization.
- **Ticket destination uncertainty example:** [Destination Estimation for Bus Passengers Based on Data Fusion](https://onlinelibrary.wiley.com/doi/10.1155/2020/8305475) studies destination inference using multiple evidence sources. CrowdWise has no linked passenger history/GPS ground truth from that study, so it does not adopt the inferred-alighting method.
- **DuckDB:** [official documentation](https://duckdb.org/docs/). Used for local columnar ETM ingestion and aggregation. Actual performance is measured in `performance-report.md`; no speedup is presumed from product claims.
- **FastAPI:** [response models](https://fastapi.tiangolo.com/tutorial/response-model/). Supports output validation and OpenAPI generation; CrowdWise schemas remain the actual contract.

## Follow-up acquisition checklist

For every future feed, save the untouched ZIP privately, capture publisher, access route, authorization/terms, source URL, retrieval timestamp, SHA-256, feed `feed_info`/calendar service range and validation notices. Run the local importer and (where practical) MobilityData validator. Only activate the feed for scheduled queries if required integrity checks pass and relevant service dates cover the user's query date. Do not rename an expired feed to make it appear fresh.

Detailed dated investigation, field-by-field availability, current DTC PDF provenance and the decision not to transcribe it into route data are documented in [Delhi data acquisition report](delhi-data-acquisition-report.md).
